# Pass Manager — API

REST API for **Pass Manager**, a password manager being rebuilt as a
**zero-knowledge** application: vault items will be encrypted in the browser,
and the server will only ever store ciphertext.

> **Status: v2 in progress.** The project started in 2023 as a learning
> playground and is now being audited and rebuilt milestone by milestone.
> See [docs/ROADMAP.md](docs/ROADMAP.md) for the plan and progress.
>
> ⚠️ Vault data is **not encrypted yet** (milestone M2). Authentication,
> per-user authorization and brute-force protection are in place (M1), but
> do not store real secrets until client-side encryption lands.

The web client lives in a separate repository (`pass-manager`).

## Getting started

### With Docker (recommended)

Requires Docker with Compose v2.

```bash
cp .env.template .env
# Set JWT_SECRET to a random value of at least 32 characters, e.g.:
#   openssl rand -base64 48
docker compose up --build
```

The API listens on <http://localhost:3000> (override with `API_PORT=4000 docker compose up`)
and Swagger UI is available at <http://localhost:3000/api/docs>.
Compose starts its own MongoDB, so `MONGODB_URL` from `.env` is ignored there.

### Local development

Requires Node.js 22 (`nvm use`) and a MongoDB instance.

```bash
npm install
cp .env.template .env   # then fill in MONGODB_URL and JWT_SECRET
npm run dev             # API with auto-reload + OpenAPI spec regeneration
```

## Configuration

All variables are validated at startup; the process exits with a list of
problems if anything is missing or malformed. See [.env.template](.env.template).

| Variable | Required | Default | Description |
|---|---|---|---|
| `MONGODB_URL` | yes | — | `mongodb://` or `mongodb+srv://` connection string |
| `JWT_SECRET` | yes | — | JWT signing secret, at least 32 characters |
| `NODE_ENV` | no | `development` | `development`, `test` or `production` |
| `PORT` | no | `3000` | HTTP port |
| `USE_PROXY` | no | `false` | Trust `X-Forwarded-*` headers from a reverse proxy |
| `LOG_LEVEL` | no | `info` (`silent` in tests) | pino log level |
| `FRONTEND_URL` | no | `http://localhost:5173` | Front end that receives the Google sign-in redirect |
| `CORS_ORIGINS` | no | `FRONTEND_URL` | Comma-separated browser origins allowed to call the API |
| `ACCESS_TOKEN_TTL_MINUTES` | no | `15` | Access token lifetime |
| `REFRESH_TOKEN_TTL_DAYS` | no | `7` | Refresh token lifetime |
| `COOKIE_SECURE` | no | `true` in production | `Secure` flag of the refresh-token cookie |
| `COOKIE_SAME_SITE` | no | `strict` | `strict`, `lax` or `none` (requires `COOKIE_SECURE=true`) |
| `RATE_LIMIT_WINDOW_MINUTES` | no | `15` | Window of the per-IP rate limits |
| `AUTH_RATE_LIMIT_MAX` / `API_RATE_LIMIT_MAX` | no | `20` / `300` | Requests per window on `/auth/*` / the rest of the API |
| `LOGIN_MAX_FAILED_ATTEMPTS` / `LOGIN_LOCKOUT_MINUTES` | no | `5` / `15` | Account lockout after consecutive failed sign-ins |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | no | empty | Enable "Sign in with Google" when both are set |

## Security model (current)

- **Secure by default:** every `/api/v1` route requires
  `Authorization: Bearer <access token>` except register, login, refresh,
  logout and the Google sign-in flow.
- **Sessions:** access tokens are JWTs (HS256, pinned issuer/audience) valid
  for 15 minutes. Refresh tokens are opaque random values stored only as
  SHA-256 hashes and sent in an `HttpOnly; Secure; SameSite` cookie scoped to
  `/api/v1/auth`. They rotate on every use; reusing a rotated token revokes the
  whole session.
- **Authorization:** notes, vaults and field values are always scoped to the
  authenticated user; another user's resource answers `404`. Owners come from
  the token, never from the request body.
- **Brute force:** per-IP rate limits and a temporary account lockout that
  responds exactly like wrong credentials (no user enumeration).
- **Google sign-in:** the API redirects to the front end with a 60-second,
  single-use code (never a token), exchanged via `POST /auth/oauth/exchange`.
  Only verified Google emails are accepted.
- **Hardening:** strict input validation (unknown fields rejected), 100 kb
  JSON limit, CORS allowlist, helmet headers, one error format
  (`{ error: { code, message, details? } }`) without internal details, and
  structured logs with secrets redacted.

## API overview

All endpoints are versioned under `/api/v1`. The OpenAPI 3 spec is generated
from the controllers by tsoa into `public/swagger.json` and served with
Swagger UI at `/api/docs` (use **Authorize** with an access token).

| Endpoint | Description |
|---|---|
| `POST /auth/register` | Create an account |
| `POST /auth/login` | Get an access token (refresh token set as cookie) |
| `POST /auth/refresh` | Rotate the refresh cookie and get a new access token |
| `POST /auth/logout` | Revoke the current session |
| `GET /auth/oauth/google` → `POST /auth/oauth/exchange` | Google sign-in |
| `GET /users/me` | Profile of the authenticated user |
| `GET, POST /vaults` · `GET, PUT, DELETE /vaults/:id` | Vaults of the authenticated user |
| `POST /fieldValues` | Add a field value to one of your vaults |
| `GET, POST /notes` · `GET, PUT, DELETE /notes/:id` | Notes of the authenticated user |
| `GET, POST /fields` | Field definitions catalog |

## Tests

```bash
npm test
```

Integration tests run the real Express app against an in-memory MongoDB
(mongodb-memory-server). They cover authentication, sessions, authorization
between users, brute-force protection, validation and error handling.
