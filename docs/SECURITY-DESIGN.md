# Security design — zero-knowledge vault

Status: **accepted** (M2). Decision record: [ADR-001](adr/001-client-side-encryption.md).

This document is the contract between the front end and the API for everything related to keys and
encrypted data. If an implementation disagrees with it, the implementation is wrong or this document
must be updated first.

## 1. Goals

- **Zero knowledge:** the server never receives the master password, any key that can decrypt the
  vault, or any vault content in plain text.
- **Database dump resistance:** a full copy of the database (or a backup) does not reveal any secret
  without brute-forcing each user's master password through a deliberately slow KDF.
- **Cheap master password change:** changing the master password must not require re-encrypting every
  item.
- **Crypto agility:** algorithms and parameters are versioned, so they can be upgraded without breaking
  existing data.

### Non-goals

- **Account recovery without the master password.** If it is lost, the vault is lost. This is
  intentional and is shown to the user at sign-up.
- **Protecting against a server that serves malicious JavaScript.** This is a structural limit of web
  clients; it is mitigated by CSP and by serving the client from the same origin, not solved (see §10).
- **Hiding account metadata** (email, names, number of items, item types, timestamps, sizes).

## 2. Threat model

| Adversary | Capability | Outcome |
|---|---|---|
| Database or backup leak | Reads every collection | Gets only ciphertext, KDF salts and a slow hash of `authHash`. Each account needs an offline PBKDF2 brute force (600k iterations), plus bcrypt for the auth path. |
| Curious or compromised server operator (passive) | Reads every request and the database | Same as above. `authHash` is seen at login, but it cannot decrypt anything (separate HKDF branch). |
| Network attacker | Observes or modifies traffic | Defeated by HTTPS (HSTS via helmet). Cookies are `Secure`, `HttpOnly`, `SameSite=Strict`. |
| Another user of the service | Uses the API with their own account | Ownership checks (M1) plus AAD binding (§5) prevent reading or swapping other users' items. |
| Attacker with a stolen, unlocked device | Uses the open tab | Mitigated by auto-lock: the key is wiped from memory after inactivity (ZK-08). |
| XSS in the front end | Runs script in the app's origin | Out of scope for crypto; mitigated by React escaping, a strict CSP and keeping keys out of storage. |

## 3. Key hierarchy

```
master password ──PBKDF2-SHA256(salt, 600 000 it.)──▶ masterKey (256 bit, never leaves the browser)
                                                         │
                       ┌───────HKDF-SHA256 "pass-manager/auth/v1"───────┐
                       │                                                │
                       ▼                                                ▼
             authKey ──base64──▶ authHash                    wrapKey (HKDF "pass-manager/wrap/v1")
             (sent to the server, which stores                │
              bcrypt(authHash))                               │ AES-256-GCM
                                                              ▼
                       userKey (random 256 bit, generated once at sign-up)
                       stored on the server only as protectedUserKey = Enc(wrapKey, userKey)
                                                              │ AES-256-GCM, one IV per encryption
                                                              ▼
                                                     vault items (encrypted)
```

- **Master password:** normalized with Unicode NFKC and UTF-8 encoded before derivation. The client
  enforces a minimum of 12 characters and shows a strength estimate (FEAT-01).
- **Salt:** 16 random bytes generated by the client at sign-up (and again at every master password
  change), stored by the server in clear. The salt is not secret.
- **KDF:** `PBKDF2-HMAC-SHA256` with **600 000** iterations (OWASP 2023 recommendation, native in
  WebCrypto). The parameters are stored per user (`kdf`) so they can be raised or switched to Argon2id
  later without a breaking change.
- **HKDF:** `HKDF-SHA256` with an empty salt and the labels above. The two branches are independent:
  knowing `authHash` reveals nothing about `wrapKey`.
- **userKey:** a random AES-256 key created with `crypto.getRandomValues`. Everything is encrypted with
  it, never with a password-derived key. That is why changing the master password only re-wraps this
  key (§7).
- **Server side:** the API stores `bcrypt(authHash, cost 12)`. This means a database leak cannot be
  replayed as a login credential, and the auth path costs extra to brute-force.

## 4. Encrypted value format (`EncString`)

Every encrypted value is a JSON object:

```json
{ "v": 1, "alg": "A256GCM", "iv": "<base64, 12 bytes>", "ct": "<base64, ciphertext + 16-byte tag>" }
```

- `v`: format version. Clients must reject unknown versions.
- `alg`: always `A256GCM` in v1 (AES-256-GCM, 128-bit tag).
- `iv`: a fresh random 96-bit IV for every encryption. Never reuse an IV with the same key.
- `ct`: the WebCrypto `encrypt` output (ciphertext followed by the tag).

The server validates the **shape** of an `EncString` (version, algorithm, base64, IV length, maximum
size) but can never validate its content.

## 5. Additional authenticated data (AAD)

AES-GCM AAD binds each ciphertext to its context, so the server cannot move it elsewhere without
decryption failing:

| Ciphertext | AAD (UTF-8) |
|---|---|
| `protectedUserKey` | `pass-manager:user-key:v1` |
| Vault item | `pass-manager:item:v1:<userId>:<itemId>:<type>` |

- `itemId` is a UUID v4 **generated by the client** when the item is created, so it is known before
  encryption. The server uses it as the item's id.
- `userId` is the id returned in `user._id`.
- Swapping two items, changing an item's type or copying an item into another account makes
  decryption fail on the client, which must surface it as a tampering error.

## 6. Vault items

```json
{
  "id": "3f6c2a1e-8d4b-4c7a-9e2f-5b1d0c9a8e7f",
  "type": "login",
  "data": { "v": 1, "alg": "A256GCM", "iv": "…", "ct": "…" },
  "revision": 3,
  "createdAt": "…",
  "updatedAt": "…"
}
```

- **Readable by the server:** `id`, `type` (`login` | `secureNote` | `card`), `revision`, timestamps
  and the size of `data`.
- **Encrypted:** everything else, including the item's name, which the server never sees.
- **`revision`:** incremented by the server on every update. Updates must send the revision they were
  based on; a mismatch returns `409` so that two devices cannot silently overwrite each other.

Plaintext schemas (the JSON that is encrypted, `schemaVersion: 1`):

| Type | Fields |
|---|---|
| `login` | `name`, `username`, `password`, `uris: string[]`, `notes`, `totp?` |
| `secureNote` | `name`, `notes` |
| `card` | `name`, `cardholderName`, `number`, `expMonth`, `expYear`, `code`, `brand?` |

Common optional fields: `favorite: boolean` and `tags: string[]`. They are encrypted as well; sorting
and filtering happen on the client (ZK-07).

## 7. Flows

### Sign-up

1. Client: generates `salt` and `userKey`, derives `masterKey`, `authHash` and `wrapKey`, and computes
   `protectedUserKey`.
2. `POST /auth/register` with
   `{ email, firstName, lastName, displayName?, authHash, kdf: { name: 'PBKDF2-SHA256', iterations, salt }, protectedUserKey }`.
3. Server: validates formats and `kdf.iterations ≥ 600 000`, then stores `bcrypt(authHash)`, `kdf` and
   `protectedUserKey`.

### Sign-in

1. `POST /auth/prelogin { email }` returns `{ kdf }`. For an unknown email the server answers with
   **deterministic fake parameters** (salt = `HMAC-SHA256(server secret, email)` truncated to 16 bytes,
   default iterations), so the response does not reveal whether the account exists.
2. Client: derives `authHash` and `wrapKey`.
3. `POST /auth/login { email, authHash }` returns the M1 session response plus `{ kdf, protectedUserKey }`.
4. Client: decrypts `protectedUserKey` with `wrapKey` to obtain `userKey`, which is kept **in memory
   only**.

### Unlock (page reload or auto-lock)

The session (access + refresh token) survives a reload, but `userKey` does not. The client:

1. Restores the session through `POST /auth/refresh`.
2. Calls `GET /users/me/keys`, which returns `{ kdf, protectedUserKey }`.
3. Asks for the master password, derives `wrapKey` and decrypts `protectedUserKey`.

A wrong master password makes the GCM decryption fail locally; no request is needed to verify it.

### Master password change

1. Client: verifies the current password by deriving it, derives the current `authHash`, generates a
   new `salt`, derives a new `authHash` and `wrapKey`, and re-wraps the **same** `userKey`.
2. `POST /auth/change-master-password { currentAuthHash, newAuthHash, kdf, protectedUserKey }`.
3. Server: verifies `currentAuthHash`, updates the credentials atomically, revokes every refresh token
   family of the user (all other devices are signed out) and returns a new session.
4. Items are **not** re-encrypted. Rotating `userKey` itself (needed only if it is suspected to be
   compromised) is a separate future feature.

### Google sign-in

Google authenticates the session but cannot provide encryption keys. On the first Google sign-in the
account has no keys yet:

1. `GET /users/me/keys` returns `404 KEYS_NOT_SET`.
2. The client asks the user to create a master password and calls `PUT /users/me/keys` with
   `{ kdf, protectedUserKey }`. This is allowed **only once** (`409` afterwards), so a stolen session
   cannot replace the keys.
3. Unlocking always requires the master password, even after a Google sign-in.
4. Google-only accounts have no `authHash`, so they cannot use the master password change flow yet
   (future feature).

## 8. What the server stores

| Data | Stored as | Readable by the server? |
|---|---|---|
| Email, first and last name, display name | Plain text | Yes (account metadata) |
| Master password | Never sent | — |
| `authHash` | `bcrypt(authHash)` | No |
| KDF parameters and salt | Plain text | Yes (not secret) |
| `userKey` | `protectedUserKey` (`EncString`) | No |
| Item content (including names) | `EncString` | No |
| Item type, revision, timestamps, size | Plain text | Yes |
| Refresh tokens and OAuth codes | SHA-256 hash | No |

## 10. Known limitations

- **Malicious client code:** a compromised server could ship modified JavaScript that leaks the master
  password. Mitigations: same-origin delivery, a strict CSP without `unsafe-eval`, and no third-party
  scripts. Browser extensions or signed builds would be the real fix (out of scope).
- **Metadata:** email, names, item count, types, sizes and timestamps are visible to the server.
- **Weak master passwords:** they remain brute-forceable offline after a database leak, just slowly.
  Hence the minimum length and the strength meter.
- **Legacy data:** accounts and vaults created before M2 used server-side password hashing and plain
  text data. They are not migrated: M2 is a breaking release, and legacy collections are dropped
  (M2-B4).
